# OpenGarden 웹 아키텍처 설계 v1

> 결론 먼저: **정적 사이트(Vercel) + 서버리스 함수 2개 + 에어테이블(데이터 원본)**.
> 데이터는 절대 HTML에 넣지 않고, 사이트가 열릴 때 API로 받아온다.

---

## 1. 전체 구조

```
[사용자 브라우저]
   │  HTML/CSS/JS (정적 파일)
   ▼
[Vercel 호스팅 — 자체 도메인 연결]
   │
   ├─ GET  /api/catalog  ──→ 에어테이블 Master DB 읽기 (가격 필드 제거 후 전달)
   └─ POST /api/quote    ──→ 에어테이블 견적요청 테이블에 기록 (요청번호 발급)
                                   │
                            [에어테이블 = 유일한 데이터 원본 (미니 ERP)]
                             재고·가격·품종·견적기록 전부 여기서만 수정
```

**왜 이 구조인가**
- HTML에 데이터 저장 ❌ → 품종 1,924종을 수정할 때마다 코드를 고쳐야 하고, 가격 같은 내부 정보가 노출될 위험. 
- 에어테이블에서만 수정하면 사이트에 자동 반영 ⭕ → 브리핑의 목표 그대로.
- 서버(백엔드)를 24시간 돌릴 필요 없음 → 서버리스 함수는 요청 올 때만 실행, 사실상 무료.

## 2. 데이터 계층 (ERP 관점)

| 역할 | 지금 (1단계) | 나중에 커지면 |
| --- | --- | --- |
| 품종 마스터 | Airtable Master DB | 유지 |
| 재고·가격 | Airtable (단가_EUR + 원화 공식) | 유지 or ERP 연동 |
| 견적 접수 기록 | Airtable 견적요청 테이블 (신규) | 유지 |
| 제안서 발송 | 별도 채팅에서 진행 중인 자동화 | 견적요청 테이블과 연결 |
| 회계·세금계산서 | 별도 (더존/이카운트 등) | 필요 시 그때 도입 |

→ **지금 단계에서 별도 ERP는 불필요.** 에어테이블 Team 플랜(레코드 5만)이 그 역할을 충분히 함.
→ 핵심 원칙 하나만 지키면 됨: **같은 데이터를 두 곳에 적지 않는다.** (사이트·제안서·카톡 응대 전부 에어테이블만 바라보게)

## 3. 백엔드 상세 (서버리스 함수 2개)

### GET /api/catalog — 카탈로그 읽기
- 에어테이블 REST API로 Master DB를 View 단위로 조회
  - `즉시 출하 가능 카탈로그` / `사전 예약용 카탈로그` 두 View 활용
- 서버에서 **가격 필드(단가_EUR, 원화 단가)를 제거**하고 내보냄 → 브라우저에는 애초에 가격이 도착하지 않음 (프론트에서 숨기는 것보다 안전)
- 1,924종 = 에어테이블이 100건씩 페이지네이션 → 함수가 전부 모아 한 번에 응답
- **캐시 10분** (`s-maxage=600`) → 방문자가 몰려도 에어테이블 API 한도(초당 5회) 안전, 속도도 빠름

### POST /api/quote — 견적 요청 기록
- 받는 값: 품목 목록(SKU·수량), 성함/소속, 요청사항
- 하는 일: ① 견적요청 테이블에 레코드 생성 ② 요청번호 발급해 응답 ③ (스팸 방지: honeypot + 간단 검증)
- 프론트는 응답받은 요청번호를 카톡 복사 텍스트에 포함 → 카톡으로 온 문의와 에어테이블 기록이 매칭됨

### 보안 규칙
- 에어테이블 토큰은 **호스팅의 환경변수에만** 저장 (코드·HTML에 절대 노출 금지)
- 토큰 권한은 이 베이스 하나, 읽기+쓰기 최소 범위로 발급

### ⚠️ 호스팅 호환 주의 (정정)
- 설계(정적 파일 + 함수 2개)는 어느 호스팅이든 동일하지만, **함수 코드의 작성 형식은 서비스마다 다름**
- 현재 `api/*.js`는 Node의 (req, res) 방식 — **Vercel 계열 기준**으로 작성됨
- Netlify·Cloudflare Pages를 선택하면 핸들러 형식만 소폭 변환 필요 → 클로드 코드에 "Netlify Functions 형식으로 변환해줘"라고 요청하면 몇 분 내 처리되는 수준

## 4. 이미지 처리 ⚠️ (미리 알아야 할 함정)

에어테이블 **첨부파일(Image 필드) URL은 몇 시간 뒤 만료**됩니다. 첨부 URL을 사이트에 그대로 쓰면 사진이 깨져요. 해결책 (택1):
1. **이미지_URL 필드에 고정 URL 사용** (권장) — 이미지를 Cloudinary(무료)나 GitHub 등에 올리고 그 주소를 기록
2. /api/catalog가 호출될 때마다 새 첨부 URL을 받아 캐시 10분 내에서만 사용 (임시방편, 캐시 만료 직후 깨질 수 있음)

→ 운영 편의상 1번 권장. 촬영한 식물 사진을 한 폴더에 모아 일괄 업로드 후 URL만 에어테이블에 붙여넣는 방식.

## 5. 견적요청 테이블 (에어테이블에 신규 생성)

| 필드 | 타입 | 비고 |
| --- | --- | --- |
| 요청번호 | 텍스트 (primary) | 함수가 자동 발급 (예: Q-20260711-3F8) |
| 요청자 | 텍스트 | 성함/소속 |
| 요청사항 | 장문 | 납품 시기·현장 등 |
| 품목요약 | 장문 | "1. 품종A · P9 · 10개…" 사람이 읽는 용 |
| 품목JSON | 장문 | 원본 데이터 (자동화용) |
| 상태 | 단일선택 | 신규 / 제안서발송 / 계약 / 종료 |
| 접수일시 | Created time | 자동 |

→ 이후 제안서 자동화(별도 채팅)와 이 테이블을 연결하면 "요청 → 제안서 발송" 흐름 완성.

## 6. 프론트엔드 구성

```
public/
  index.html      홈 (v2)
  catalog.html    카탈로그 (fetch('/api/catalog')로 데이터 로드)
  service.html    서비스
  faq.html        FAQ
  about.html      회사 소개 (제작 필요)
  assets/         로고·사진·공통 css/js
api/
  catalog.js      서버리스 함수
  quote.js        서버리스 함수
```

- 지금은 순수 HTML로 충분 (페이지 5개 규모). 페이지가 더 늘거나 SEO 고도화가 필요해지면 그때 Next.js로 이전 — 이 구조 그대로 옮겨짐.
- 2,000종 필터링은 브라우저에서 처리해도 가벼움 (JSON 수백 KB 수준) → 별도 검색 서버 불필요.
